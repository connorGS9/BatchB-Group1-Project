# Your 3–5 minute banking API demonstration

## Prepare before presenting

Open PowerShell in the group repository, run `cd banking-api`, then run:

```powershell
.\.venv\Scripts\python.exe -m uvicorn main:app --host 127.0.0.1 --port 8000
```

Keep that terminal running. Open http://127.0.0.1:8000/docs in a browser. Restart the server before rehearsal/presentation if you want the sample data and ID 4 again. If you create multiple accounts, use the actual `id` returned by POST in every following step. The timing below includes clicks; read only the **Say** paragraphs aloud. The remaining notes help you answer questions.

## 1. Explain the application — 0:00–0:25

**Click/type:** Open http://127.0.0.1:8000/ in a browser tab.

**Endpoint/request:** `GET /`, no body. GET reads a resource without changing it.

**Backend:** FastAPI calls `welcome()` and returns the status dictionary as JSON.

**Expected:** `200`, `{"message":"Welcome to the Banking REST API","status":"ok","docs":"/docs"}`.

**Say:** “This is my banking REST API built with Python and FastAPI. It manages account records and demonstrates create, read, update, and delete. Each account has an ID, holder, type, and balance. The assignment asks for hard-coded data, so I start with three fictional accounts stored in memory.”

## 2. Open Swagger — 0:25–0:45

**Click/type:** Switch to http://127.0.0.1:8000/docs. Expand the **Accounts** section if collapsed.

**Endpoint/request:** The browser sends `GET /docs`, then loads `GET /openapi.json`; neither needs a body. These GET requests read documentation.

**Backend:** FastAPI serves Swagger HTML and a schema generated from the routes and models.

**Expected:** `200`, an interactive page showing GET, POST, PUT, and DELETE operations.

**Say:** “Swagger is the interactive API documentation generated by FastAPI. I can send HTTP requests here and inspect their status codes and JSON responses. It acts as my client for this demonstration.”

## 3. GET all accounts — 0:45–1:05

**Click/type:** Expand **GET /accounts**, click **Try it out**, then **Execute**. Look under **Server response**.

**Endpoint/request:** `GET /accounts`, no parameters or body. GET means read.

**Backend:** `list_accounts()` converts the account dictionary values to a list.

**Expected:** `200` and three JSON objects: IDs 1, 2, 3, with balances `"1250.50"`, `"8400.00"`, `"675.25"`.

**Say:** “This GET request retrieves all three sample accounts. Status 200 means success. The response is a JSON array. Reading the accounts does not change the stored data.”

## 4. GET an account by ID — 1:05–1:25

**Click/type:** Expand **GET /accounts/{id}**, click **Try it out**, enter `1` in **id**, click **Execute**.

**Endpoint/request:** `GET /accounts/1`, no body. GET reads one resource; `1` is the path parameter.

**Backend:** `get_account()` calls `require_account(1)` to look up ID 1 in the dictionary.

**Expected:** `200`, `{"account_holder":"Avery Johnson","account_type":"checking","balance":"1250.50","id":1}`. JSON field order is unimportant.

**Say:** “Here the ID in the URL selects one account. The backend finds ID 1 and returns Avery Johnson’s account. This shows the read operation for a specific resource.”

## 5. POST a new account — 1:25–1:55

**Click/type:** Expand **POST /accounts**, click **Try it out**, replace the entire request body with:

```json
{
  "account_holder": "Taylor Brown",
  "account_type": "savings",
  "balance": "500.00"
}
```

Click **Execute**. Note the returned **id** (4 on a fresh server).

**Endpoint/request:** `POST /accounts`, `Content-Type: application/json`, body above. POST creates a new resource in this collection.

**Backend:** Pydantic validates the fields. `create_account()` assigns the next ID, stores the account, increments the counter, and sets a Location header.

**Expected:** `201`, the submitted fields plus `"id":4`; response header `location: /accounts/4`.

**Say:** “POST creates a new account. I send the editable fields as a JSON request body, and the server assigns the ID. Pydantic checks the input before it is stored. Status 201 means created. The new account has ID 4.”

If a different ID appears, say that ID and use it below.

## 6. GET the new account — 1:55–2:15

**Click/type:** Return to **GET /accounts/{id}**. Change **id** to `4` (or the returned ID), then click **Execute**. If editing is disabled, click **Try it out** first.

**Endpoint/request:** `GET /accounts/4`, no body. GET reads the new resource.

**Backend:** Looks up the newly stored dictionary entry.

**Expected:** `200`, Taylor Brown, savings, balance `"500.00"`, ID 4.

**Say:** “I now retrieve the new ID in a separate request. The response confirms that the create operation stored the account in memory.”

## 7. PUT an update — 2:15–2:45

**Click/type:** Expand **PUT /accounts/{id}**, click **Try it out**, enter `4` in **id**, and replace the request body with:

```json
{
  "account_holder": "Taylor Brown",
  "account_type": "savings",
  "balance": "750.25"
}
```

Click **Execute**.

**Endpoint/request:** `PUT /accounts/4`, `Content-Type: application/json`, complete body above. PUT replaces the editable representation at this ID.

**Backend:** Validates all fields, checks the account exists, and replaces the dictionary entry while preserving ID 4.

**Expected:** `200`, Taylor Brown’s account with balance `"750.25"`.

**Say:** “PUT updates this existing account. I provide all editable fields and change the balance to 750.25. The ID stays the same. This is a record update for the CRUD assignment, not a banking transfer.”

## 8. GET again to confirm the update — 2:45–3:05

**Click/type:** In **GET /accounts/{id}**, keep **id** `4` and click **Execute** again.

**Endpoint/request:** `GET /accounts/4`, no body. GET reads the current stored state.

**Backend:** Retrieves the replacement entry.

**Expected:** `200`, balance `"750.25"`.

**Say:** “A separate GET confirms the updated balance. The response reflects the stored data, rather than only the previous update request.”

## 9. DELETE the account — 3:05–3:25

**Click/type:** Expand **DELETE /accounts/{id}**, click **Try it out**, enter `4` in **id**, click **Execute**.

**Endpoint/request:** `DELETE /accounts/4`, no body. DELETE removes the specified resource.

**Backend:** Checks the account exists, then removes the dictionary entry.

**Expected:** `204`, with no response body. Swagger may display “No content.”

**Say:** “DELETE removes the account. Status 204 means the operation succeeded and there is no response body.”

## 10. GET again to show 404 — 3:25–4:00

**Click/type:** Return to **GET /accounts/{id}**, keep **id** `4`, click **Execute**.

**Endpoint/request:** `GET /accounts/4`, no body. GET attempts to read the deleted resource.

**Backend:** `require_account()` cannot find the ID and raises an HTTP exception.

**Expected:** `404`, `{"detail":"Account 4 not found"}`.

**Say:** “The same GET now returns 404 because the account no longer exists. This completes create, read, update, and delete. I also tested invalid input and missing accounts. The automated suite has 42 passing tests, and a live HTTP check verifies the real server. Restarting the server resets everything to the hard-coded samples.”

## Optional validation demonstration — add 20 seconds

In **POST /accounts**, use the creation body but set `"balance":"-1"`. Click **Execute**. Expect `422` with an error pointing to `body.balance`. Say: “Pydantic rejects a negative balance before the route changes storage.” Do not confuse Swagger’s example responses with the actual **Server response**.

## Likely instructor questions

| Question | Short answer |
| --- | --- |
| What is REST? | Representational State Transfer: an architectural style using resources and a uniform interface. This API identifies account resources with URLs and operates on them using HTTP methods. |
| What is an API? | An application programming interface: a defined way for software components to communicate. Here clients exchange HTTP requests and JSON responses. |
| What is CRUD? | Create, Read, Update, Delete: the basic operations on stored records. |
| CRUD-to-HTTP mapping? | Create → POST; Read → GET; Update → PUT (or PATCH for partial updates); Delete → DELETE. |
| GET vs POST? | GET retrieves data without modifying it. POST creates a new account here. |
| POST vs PUT? | POST creates a server-assigned ID. PUT replaces all editable fields at a known ID. Repeating the same PUT has the same final state; repeating POST creates additional records. |
| What is DELETE? | The HTTP method used to remove the identified resource. Repeating it leaves the resource absent, though this API returns 404 after the first deletion. |
| What is JSON? | JavaScript Object Notation, a text format for objects, arrays, strings, numbers, booleans, and null. It is language-independent. |
| What is an endpoint? | An API operation identified by a method and URL path, such as GET /accounts. |
| What is a path parameter? | A variable in a URL path, such as the ID in /accounts/4. |
| What is a request body? | Data sent in the request, here the JSON account fields for POST and PUT. |
| What does 200 mean? | OK: the request succeeded. |
| What does 201 mean? | Created: a new resource was created. |
| What does 204 mean? | No Content: success with no response body. |
| What does 404 mean? | Not Found: the requested account does not exist. |
| What does 422 mean? | Unprocessable Content: the submitted data failed this API’s validation. |
| Why FastAPI? | It provides concise routing, typed validation integration, response serialization, and automatic OpenAPI/Swagger documentation. |
| What does Pydantic do? | Defines data schemas and validates/converts incoming values into Python model objects. |
| How is validation performed? | FastAPI applies Pydantic models before calling the route. Constraints reject blank names, unsupported types, negative or over-precise amounts, missing fields, and extra fields. Path IDs must be positive integers. |
| Where is the data stored? | In a Python dictionary in the running server process, keyed by integer account ID. |
| What happens after server restart? | All changes disappear and the original three sample accounts return. The next ID resets to 4. |
| Why use in-memory data? | The assignment explicitly asks for hard-coded data; it makes the CRUD behavior easy to demonstrate. |
| How would you add a real database? | Create an accounts table and replace dictionary reads/writes with database queries and transactions, using an ORM or database driver. Keep the route schemas and add migrations. |
| How did you test it? | 42 pytest cases use fresh FastAPI TestClient instances without mocks. A separate script starts Uvicorn and checks real HTTP CRUD, Swagger assets, OpenAPI, validation, and missing records. |
| Walk me through a request from client to response. | Swagger sends HTTP to Uvicorn. FastAPI matches the route, validates path/body with Pydantic, calls the handler, reads or changes the dictionary, validates/serializes the result, and sends JSON plus a status code back. |
| Why is balance a string in JSON? | Internally it is Decimal for exact decimal values. A two-decimal string avoids loss of precision in clients that parse JSON numbers as binary floating point. |
| Is this stateless if there is a dictionary? | REST statelessness concerns client session context: each request contains what is needed to process it. Servers can still store resource state, like these accounts. |
| Why no authentication or database? | Those are outside the requested training scope. This is a CRUD demonstration, not a deployable real banking service. |
